# t


一路做下来我们其实已经养成了一个特别好的习惯每次让AI动手写代码之前都会先用计划模式让他把方案想清楚跟我们确认过了再让他去执行咱们之前这种做法已经很荒用了但是一旦项目越来越复杂很多人就会开始遇到同样的问题刚让AI改完一功能另一个地方又受到影响聊到后面他可能把前面那样的规则给忽略了为什么会这样一个很重要的原因就在于项目里缺少一份大家都能反复查看白纸黑字写清楚的约定 AI在执行新的任务是需要根据当前上下文里能够拿到的信息继续判断如果一些重要的要求没有被明确记录下来或者随着对话越来越长被埋在前面的内容里它就更容易遗漏所以这节我们就来给执行的做法再做一次升级我们要学习的是一套和AI协作开发式非常实用也更加成体系的方法叫做SDD 全称是Spec Driven Development 中文到的规范驱动开发可以把它理解成之前先确认方案再执行的加强版我们不再只是让AI在对话里给我们一份计划而是把原来散落在对话里的需求规则和方案正式沉淀成一套能查阅

能对照的文档具体来说我们会参考GitHub Spec Kit的思路 GitHub Spec Kit是GitHub推出的一套规范驱动开发的工具和工作流把这条主线分成主要的四部 Constitution 项目原则 Specify 项目规格 Plan 技术计划 Tasks 任务清单最后才是Implement 实现其中Constitution更像是整个项目长期遵守的宪法而后面的Specify Plan Tasks Implement 是每个功能都可以反复经历的一套核心开发流程下面我们就一个一个来看第一步叫Constitution 我们可以把它理解成项目的宪法或者章程它关注打是那些不管以后做什么功能都要一直遵守的长期规则至于某一个具体功能到底怎么做并不归他管比如一个团队可以提前约定界面要优先适配手机屏幕不记录没有必要的用户个人信息每增加一个新功能都要配上对应的测试提到代码也要遵守同一的规则那为什么要专门把这些规则单独写出来呢因为AI在面对好几种都能实现的方案是需要自己做

选择如果我们没有提前给它划清边界它可能今天选这个组件库明天又换一个这次记得补测试下次它又忘了而Constitution的作用就是提前把必须一直遵守的底线说清楚那一份Constitution到底应该写些什么呢对于我们初学者做的项目来说其实不用写的特别复杂先写三到五条最重要的规则就够了内容大致可以分成三类这里以一个社区活动报名的项目来作为例子第一类是核心原则比如仅收集报名所必须的个人信息不留存任何非必要用户隐私数据第二类是技术约束比如前端统一沿用项目现有的技术方案不引入功能重复的第三方库第三类是质量要求比如关键操作如果之前失败必须向用户返回明确的错误提示最后再提醒一下 Constitution里不会写用户可以在系统里报名活动这类内容因为用户可以报名描述的是一个具体功能

这些规则一般来说都由我们人来定因为它代表的是这个项目长期检守的底线和原则这是原则可能来自行业里约定俗成的规范也可能来自团队自己的要求但到底哪些事情最重要哪些边界不能碰这个方向还是得我们自己拿主意当然如果你一时不照该从哪里开始也可以让AI先帮你起一般草稿再由我们自己来检查修改和确认那不管是我们自己写还是让AI先帮忙起草称称以后都要重点检查两件事第一这些规则是不是真的长期有效也就是说它不应该只针对眼前某一个功能而是以后做新的功能依然需要遵守第二也是更关键的一点每一条规则能不能被检查我们要能够比较清楚的判断最后到底是遵守了还是没有遵守比如做一个优秀的产品听起来当然没问题但这句话太空了什么叫优秀做到什么程度算优秀后员既没办法用它指导具体工作也没办法拿它检查成果那么针对这种规则我们就要继续把它改得更具体更明确直到它真正能够指导后面的需求技术方案和代码实现接下来这一部叫Specify 也就是需求规格很多人一有了想法就直接跟AI说帮

我做一个社区活动报名功能这句话拿来开个头可以但还远远不够成为真正的开发依据因为AI一听到这句话马上就会遇到一连串需要自己猜的问题到底谁能报名名额马力以后怎么办远不允许取消报名成功以后用户应该看到什么那这些问题如果我们不提前说清楚 AI就只能自己替我们补全但它补出来的答案未必就是我们真正想要的所以Specify做的事情就是把这些我们平时觉得默认谈刺斗动实际上却从来没有说清楚的内容正式写下来它的定位很明确主要回答两个问题我们到底要做什么以及为什么要做至于技术上具体怎么实现那是下一步plan阶段要解决的事情这一步先不碰我们可以把Specify理解成一份站在用户和产品视角把需求说清楚的说明文档它主要有三个很实际的作用第一个是消除歧义把用户可以报名这种比较笼统的说法进一步拆成具体的用户行为条件和结果第二个是滑定范围明确这一版到底要做什么又有哪些东西暂时不做避免项目做着做着功能越来越多最后还完全说不住第三个是提供验收依据功能做完以后我们就不用再凭感

觉判断好像差不多了而是可以直接拿着需求规格一条一条对照检查我们还是拿社区活动报名这个项目举例最开始我们可能只有这样一个比较朴素的想法这是一个给社区居民使用的活动报名服务居民希望看到附近有哪些活动在确认时间和地点以后完成报名报名成功以后还能收到一个确认这句话其实已经交代了几个很重要的信息谁会使用它要解决什么问题以及大概的使用流程是什么一轮先把需求收到这个程度就已经足够我们继续往下整理了接下来就可以让AI把这段大白话整理成一份更规范的SPEC.

MD 初版的需求规格不用追求一次性就写的面面俱到最重要的是先让AI按照一个统一的格式把我们脑子里原本比较零散的想法清清楚楚的整理出来展示在文档里那些更细的业务规则各种异常情况还有一些边界和限制我们完全可以放到后面通过一轮轮的审阅和证据慢慢补充进去这份初版规格里我们要重点关注两个最重要的部分第一个是功能需求可以尽量使用用户可以什么什么这样的句式把用户到底需要完成什么事情写清楚比如用户可以查看活动的时间地点和剩余名额

第二个是验收标准也就是进一步写清楚到底出现什么结果才算这个需求真正完成了比如当活动名额已满是报名入口显示为满源状态用户无法继续提交报名这样一来大家看的都是同一份文档同一套标准以后如果对某个功能产生争议就可以直接回到这份spec里面对照判断现在算出来的结果到底符不符合我们之前确认好的需求另外写spec的时候还有一个很重要的原则先用业务语言也就是代表话把事情说清楚但是不要把技术方案塞进来比如把报名结果保存到某某数据库带有某某接口这种话讲的其实都是怎么实现这些内容应该留到下一步plan的时候才决定也就是先把硬要做什么说清楚后续再讨论怎么做这样需求和技术方案才不会混在一起那还有一个很实用的做法就是在spec里专门留一个以后再做的区域那些第一版暂时还不需要的功能可以先放到这里而不是一想到就马上塞进当前版本这样可以帮助我们给产品划清边界避免范围越做越大那生成了出版以后也别急着马上进入技术计划在实际操作里我们通常还会做两天特别

重要的事情第一件是逐条省约哪里有问题就只让AI修改我们指定的那一小块因为改动范围越大越容易把原本已经确认好的内容也一起改掉第二件是让AI主动帮我们做澄清我们可以让它检查这份spec里面还有哪些地方比较模糊互相矛盾或者存在遗漏然后把这些问题一条一条列出来我们负责回答 AI再根据我们的答案把结果写回到文档里就这样一轮一轮的审约提问补充初版的spec会慢慢变成一份真正可以拿去直到后续开发和验收的规格文档等需求规格确认好了以后我们进入第三部 Plan 也就是技术计划前面的specify主要负责回答要做什么而到了Plan这一步我们要解决的就是具体准备怎么做这时候我们会让AI同时参考两份很关键的文档一份是第一部写好的Constitution 它告诉AI这个项目有哪些长期原则和底线是后面的技术方案不能违反的另一份是第二部确认好的spec 它告诉AI这次具体要满足哪些用户需求以及最后要达到什么样的结果而Plan要做的就是把这两份东西真正串起来把spec里面一

条条产品需求翻译成一套可以落地的技术实现方案同时保证整个方案没有违反Constitution里的原则那一份比较完整的技术计划通常会包含哪些内容呢比如这次计划对应的是哪一份spec 当前项目使用的是什么技术方案需要新增或者修改哪些数据页面和不同模块之间要怎么配合

实现的时候可能涉及权限判断某些数据需要在不同模块之间保持同步到外部服务失败以后需要考虑怎么处理这些问题如果等代码都想到一半才发现很可能就要重新改加构改数据甚至推到一部分重来那生成这份技术方案的时候我们可以这样给AI提要求如果你是没有太多技术背景的数学者应该怎么检查这份Plan呢我们其实完全不需要一上来就看到里面的每一个技术名词只需要牢牢抓住三个问题第一 Plan有没有覆盖spec里的每一条重要需求不能需求力显的一件事技术计划最后只考虑了三件第二这套方案有没有违反constitution里定好的规则比如我明明规定了尽量复用项目现有技术 Plan却引入了一套空中重复的新框架那就需要重新确认第三那些比较容易出问题的地方 Plan有没有提前说明准备怎么处理和验证比如权限数据一致性接口失败这些风险有没有对应的处理方案和测试方法这三个问题里面只要有任何一个你觉得还没有说清楚的就先不要着急开始起来先让AI把Plan补清楚确认方案没问题以后再进

入下一步第四步 Tasks任务清单如果说上一步的Plan 帮我们解决的是路线问题也就是这件事整体准备怎么做那这一步的Task 解决的就是执行顺序的问题也就是具体先做什么后做什么它会把前面的一整套技术方案继续拆成一张可以逐项执行的任务清单那什么样的任务才算拆的比较好呢通常有三个特点第一一次只做一件主要的事第二做完以后能够被单独验证第三它和其他任务之间的依赖关系是清楚的知道哪些事情必须先做哪些事情可以后座比如如果任务直写一句完成活动报名系统这个范围就太大太笼统了 AI很难稳定的一次全部做好一旦中间出了问题我们也很难判断到底哪一个环节出了错但如果把它继续拆开就可以变成先建立活动相关的数据结构但实现报名资格调研然后完成报名页面接着补充报名失败时的提示最后给报名规则加上测试这样一拆每一步都变得更加具体 AI每次只需要集中解决一个问题我们也能在每一步结束后先检查结果确认没问题再继续往下做对应的提示词可以这样写可以看到在这个提示词里

我们要求AI针对每一条任务都要把四件事写清楚这一步要完成什么目标混音像哪些模块或文件依赖哪些前置任务以及做完以后准备怎么验证把这些信息写清楚以后不管后面是人类执行还是交给AI来执行拿到其中任何一条任务都能快速知道这一小步到底要做什么做完以后又该怎么判断它是不是真的完成了第五步 implement 也就是实施和验收到了这一步才终于真正轮到AI开始线代码而且这时候我们也不需要把整个项目从头到尾重新描述一遍了只需要让AI先读取前面已经确认好的几份文档 institution spec plan 和tasks 然后按照任务清单开始执行当前这一项任务而且每完成一项任务我们都要回到前面的规格文档拿着当初写好的验收标准去检查结果比如用户能不能顺利完成对应的操作各种异常情况有没有被正确处理实现过程中有没有违反 constitution里定下的长期规则如果都符合就把这条任务勾掉继续下一项如果没有通过就明确指出到底是哪一条规格或验收

标准没有代表让AI围绕这个具体问题去修正 AI更擅长的是把一个已经说清楚的要求转化成具体实现而我们更重要的工作在聊天框里插入一句顺便再帮我加个功能而是先回到spec 把新的需求正式更新进去然后再检查plan和task 要不要跟着调整最后才进入实现不然新的需求又会重新散落回聊天记录里前面好不容易建立起的这一套依据就可能慢慢失效所以用一句话来总结这一套方法我们可以这样理解之前的提示工程更多是在解决这一轮对话里怎么把事情说清楚而SDD解决的是整个项目从头到尾怎么持续把事情说清楚下一节我们就会把这一套流程放进一个项目里从头到尾完整跑一遍我们下期再见
