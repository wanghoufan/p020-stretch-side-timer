# t


我们和AI编程工具写作一段时间以后经常会遇到一个现象时让AI自己检查刚刚写完的代码大总说我看了没什么问题但真正抛下以后还是会暴露出一些bug 为什么会这样呢因为AI在实现一个方案的过程里已经基于当前的需求上下文和自己的判断形成了一整套这样做是对的的思路了所有的判断权衡取舍都是围绕着这套思路展开的等我们让同一个AI回头审查的时候它很容易继续沿用刚才那套假设和判断没法跳出来看到问题所以这一节我们来学习一个很实用的技巧生成和验收分离我们先了解一下什么叫做生成和验收分离在传统的软件开发里有一个很成熟的做法就是尽量不要只让代码作者自己检查自己写的代码而是引入另外一个独立视角来做审查测试或者验收因为一个人刚刚按照自己的思路把代码写出来再马上用同一套思路回头检查很容易忽略那些一开始都没有意识到的问题换一个人来看会更容易发现需求遗漏边界情况和设计上的问题同样的思路也可以用在AI编程上我们可以把负责写代码的AI叫做生成者再找一个独立的AI来做验收者

两个角色放在不同的对话里各自完成自己的工作一个负责实现一个负责挑问题具体怎么操作呢可以分成三个步骤第一步生成这就是我们平时的做法在一个对话里让AI根据需求完成某个功能直到他把这一轮实现做完第二步验收这时候我们不要继续让原来的对话自己检查而是新开一个对话让另一个AI从头来看这份成果我们可以把原始需求验收标准以及需要检查的代码或者项目内容一起交给他然后告诉他请站在独立审查者的角度检查这份实现有没有天理需求遗漏功能边界情况没有助理或者存在其他明显问题新对话里的AI没有参与前面的实现过程他看到的主要就是需求和最终结果所以更容易提出一些生成者没有意识到的问题比如某个需求只实现了正常流程但遗漏掉了异常情况还有某个边界条件没有处理等等第三步就是闭环拿到验收者的问题现在以后不是到这里就结束了而是把真正成立的问题带回到原来的生成者对话让他针对这些反馈去修比如我们可以告诉生成者我找了一个独立视角检查这次实现发现下面几个问题请逐

条核对如果问题成立就进行修复并且重新完成对应的验证生成者修改完整以后我们再回到验收者的对话让他基于最新版本重新检查一次如果还有问题就继续反馈给生成者如果关键问题已经解决再结合自动化测试实际运行结果和验收标准确认这一轮任务可以结束所以真正有效的不只是再找一个AI看一遍而是形成一个生成验收反馈修改再验收的完整循环用这套流程的时候还有几个小细节可以让效果更好第一是给验收者足够清楚的判断依据当时把代码丢过去让他看看有没有问题而是把原始需求验收标准以及这一次具体实现了什么一起告诉他因为验收者真正要判断的不是代码写的漂不漂亮而是实现到底符不符合需求第二是要把验收反馈完整交回生成者但不要让他盲目召改我们最好保留验收者原本的问题描述原因和上下文再让生成者逐条核对这个问题到底是不是真的存在如果成立就修复并独立验证如果不成立也要说明判断依据这样做很重要因为验收者也不一定永远是对的我们真正想要的不是让一个AI听另一个AI的而是让两个独立视角互相检查最后都回到需求和实际结果上说话我们下期见
